# MLA 与 DeepSeekMoE 完整流程（含所有疑问点）

## 角色与核心思想

DeepSeek-V2 是一个 MoE 大模型：总参 236B，每 token 只激活 21B，上下文 128K。它只动 Transformer 的两个部件，各解决一种"贵"：

- **注意力 → MLA（多头潜在注意力）**：解决推理贵。MHA 的 KV cache 随着头数、层数暴涨，是批量和长上下文的最大瓶颈。MLA 把每个 token 的 k、v 联合压缩成一个 512 维 latent 向量 `c_KV`，推理时只缓存它，不再缓存 128 个头的 k/v。
- **FFN → DeepSeekMoE**：解决训练贵。细粒度专家切分 + 共享专家隔离，让"总参大、激活小"成为可能：每层 160 个路由专家里只选 6 个。

两个推演主轴：**①一次带 MLA 的前向，token 的 k,v 是怎么算、怎么缓存、怎么被"不还原"地用掉的；②一次 MoE 路由，160 个专家怎么分活、负载怎么稳、通信怎么被摁住。**

一个重要提醒：很多人把「无辅助损失负载均衡（专家偏置 b_i）」记在 V2 头上——**本文没有这个机制**。V2 靠的是三个辅助损失（专家级/设备级/通信级）+ 设备受限路由 + token 丢弃（见下文阶段详述与文末更正框）。

## 机制一：MLA——一次带低秩压缩的前向推演

### 阶段零：先算清 MHA 的账（它为什么炸）

标准 MHA（原文式 1–8）：`d` 是隐层维度，`n_h` 个头，每头 `d_h` 维。

```
式1–3:  q_t = W_Q·h_t,  k_t = W_K·h_t,  v_t = W_V·h_t
式4–6:  把 q_t、k_t、v_t 切成 n_h 份 → q_t,i、k_t,i、v_t,i
式7:    o_t,i = Σj Softmax_j( q_t,iᵀ·k_j,i / √d_h ) · v_j,i   （j 遍历前文所有位置）
式8:    u_t = W_O·[ o_t,1 ; … ; o_t,n_h ]
```

KV cache 的账：**每个 token 每层要缓存 2·n_h·d_h 个元素**（k 和 v 各 n_h·d_h）。V2 这种 128 头 × 128 维的配置就是每 token 每层 32768 个元素，乘上 60 层、乘上千上万 token，显存先炸，带宽跟着炸。

**疑问点①：为什么 GQA/MQA 减缓存是"拆东墙补西墙"？**
GQA 减少头的分组数（组内共享 k/v），MQA 干脆全层共享一组 k/v。缓存确实小了，但表达能力跟着掉——本文附录 D.1 的消融做了实证：7B 模型分别用 MQA、GQA(8组)、MHA 训 1.33T token，MMLU 是 37.9 / 41.2 / 45.2（原文表8），MHA 明显最强。**旧思路是裁编制：GQA/MQA 直接砍掉一部分服务员；MLA 的思路是压缩打包菜单：服务员不变，每单的点菜单被压成一小张。**

### 阶段一：KV 联合低秩压缩（式 9–11）

MLA 的第一条腿——**k 和 v 不是从 h_t 直接生成，而是先一起塞进一个小瓶子**：

```
式9:  c_KV(t) = W_DKV · h_t          h_t ∈ R^d → c_KV(t) ∈ R^d_c   （d_c=512 ≪ n_h·d_h=16384）
式10: k_C(t)  = W_UK  · c_KV(t)      还原出 128 个头的内容 k（纯内容、无位置信息）
式11: v_C(t)  = W_UV  · c_KV(t)      还原出 128 个头的内容 v
```

**疑问点②：512 维真的装得下 16384 维的内容吗？凭什么低秩可行？**
作者赌的是：**k 和 v 的信息是低秩的**——16384 维里真正自由变化的维度远没有那么多。k、v 又来自同一个 h_t，联合压缩还能共享公共因子。两个证据：(a) 压缩瓶颈处显式加了 RMSNorm + 缩放因子稳住训练（原文 3.1.2），说明这是刻意设计的深瓶颈；(b) 附录 D.2 的对照实验：同规模 MoE 模型，MLA 比 MHA 少了 96% 的缓存还更强（大模型 MMLU 59.0 vs 57.5，BBH 50.7 vs 46.6，原文表9）。**低秩不是假设一厢情愿，是拿了分数验证的设计。**

**疑问点③：训练时反正要把 k_C/v_C 还原出来，压缩图什么？不是多此一举？**
图的是**缓存是一个 token 存过的东西，训练算过的临时量可以丢**。前向中 W_UK/W_UV 随手就用现算的 c_KV 还原 k/v（显存里活一毫秒），算完注意力就扔；但只有 `c_KV` 进缓存，一直活到推理时被反复读。**压缩省的不是"这一次计算"的内存，而是"历史 token 遗产"的内存（KV cache）。**

### 阶段二：Q 也压一道（式 12–13）

```
式12: c_Q(t)  = W_DQ · h_t           h_t → c_Q(t) ∈ R^d_c′  （d_c′=1536）
式13: q_C(t)  = W_UQ · c_Q(t)        还原出内容部分 q
```

**疑问点④：压缩 Q 省不了 KV cache，压它干嘛？**
原文自己说得明白：**"为了减少训练时的激活内存"（activation memory）**。训练时 4K 序列上一个 token 的 q 也有 16384 维，Q 走低秩压缩能把激活体积显著压下去。注意：q 只属于当前 token，不进缓存，所以这一步对 KV cache 是零贡献——**它是训练侧的开销优化，和缓存无关。**

### 阶段三：RoPE 撞车压缩（最容易卡住的地方）

DeepSeek 67B 起，模型用 RoPE 注入位置。但 RoPE **对 k 和 q 都是位置敏感的**（k 的旋转角取决于 token 自己的位置索引），这和"压缩"正面冲突：

- 压缩链路里 k 是从 `c_KV` 还原出来的：`k_C = W_UK·c_KV`。若在这里施加 RoPE，等价于让矩阵乘多了一层"随 token 位置变化的旋转向量"夹进 `W_UK` 中。
- 推理时原本想把 `W_UK` 折进 q 侧一路玩"不还原"（见阶段四）。但矩阵乘不满足交换律：RoPE 矩阵会楔在 `W_UQ` 与 `W_UK` 之间，**吸收失效，就得对每个前缀 token 重算 k——缓存省了个寂寞**。

**疑问点⑤：位置信息为什么不能就藏在 `c_KV` 里让它"顺手"带出去？**
因为位置必须是**逐 token 绝对不同**的（RoPE 的本质是 q 和 k 各按自己的位置旋转、点积时出相对相位）。而 `c_KV` 被全体历史 token 共享同一条还原通路 `W_UK`，通路上没法对位置 t 插入不同的操作；若对还原后的 k 统一加 RoPE 即回到上一段的吸收失效问题。**结论：位置信息必须放弃与压缩通路合流，旁路置办一条独立小路——这就是"解耦"（Decoupled）的含义。**

解耦 RoPE（式 14–17）——每个头配一个小的旋转 q，全体头共享一个小的旋转 k：

```
式14: q_R(t,i) = RoPE( W_QR · c_Q(t) )     每个 i 号头有独立的 d_hᴿ=64 维旋转 q
式15: k_R(t)   = RoPE( W_KR · h_t )        一个 token 只有一个共享旋转 k，64 维
式16: q_t,i = [ q_C(t,i) ; q_R(t,i) ]       内容段 + 位置段 拼起来
式17: k_t,i = [ k_C(t,i) ; k_R(t) ]
```

**疑问点⑥：k_R 为什么直接从 `h_t` 生成、不走 `c_KV` 压缩这条线？**
三个原因：(a) k_R 是给 RoPE 用的，位置敏感、每 token 各不相同，走压缩线会沾上"低秩前向共享瓶颈"的约束；(b) 它极小（64 维），没必要压；(c) 原文长上下文扩展（YaRN）只对 `k_R` 生效（3.1.4），k_R 独立成通路，128K 扩展才不用动主压缩链路。

### 阶段四：一次真实 MLA 前向，从头到尾

```
                                    训练时算一遍（推理时不用重算）
h_t ──┬─W_DKV─→ c_KV(t) ★缓存  ──┬─W_UK─→ k_C(t,1..n_h)
      │                          └─W_UV─→ v_C(t,1..n_h)
      ├─W_KR──RoPE────→ k_R(t) ★缓存
      └─W_DQ──→ c_Q(t) ─┬─W_UQ──→ q_C(t,1..n_h)
                        └─W_QR──RoPE→ q_R(t,1..n_h)

                                                              （推理时）
       每个 head i:  q_t,i = [q_C, q_R]，  历史每个 j 号: k_j,i = [k_C, k_R]
       式18: o_t,i = Σj Softmax_j( q_t,iᵀ·k_j,i / √(d_h+d_hᴿ) ) · v_C(j,i)
       式19: u_t = W_O·[ o_t,1 ; … ; o_t,n_h ]
```

缓存端（每 token 每层）只有两样：**`c_KV`（512 元素）+ `k_R`（64 元素）= 576 元素**。

**疑问点⑦：v 的加权求和也要读缓存，但缓存里只有 c_KV，v_C 怎么每一步续上都现算吗？**
不用。这就是"吸收"（absorb）的妙处，靠矩阵乘的结合律：

```
内容项注意力权重:
  q_C(t,i)ᵀ · k_C(j,i)
  = (W_UQ·c_Q(t))ᵀ · (W_UK·c_KV(j))      [把第 i 头拆出对应切片，示意式]
  = c_Q(t)ᵀ · ( W_UQᵀ·W_UK ) · c_KV(j)
  = c_Q(t)ᵀ · ( W_UQᵀ·W_UK ) · c_KV(j)   ← W_UQᵀ·W_UK 是个可预合并的矩阵！
```

`W_UQᵀ·W_UK` 可以**离线合并成一块新矩阵**，每一步推理直接用 `c_Q(t)ᵀ·M·c_KV(j)` 算分数 —— **缓存里那条 512 维的 `c_KV` 就是 k，不需要升维出真 k**。原文主文表述为 `W_UK` 可被吸收进 `W_Q` 侧、`W_UV` 可被吸收进 `W_O`（2.1.2），附录 C 给了完整公式（式 41–47），本质同一件事。

**疑问点⑧：那 v_C 的加权求和靠什么免算？**
同理，v 那边不需要先还原 v_C：注意力算完的加权系数对 v_C(j) 加权、再经 W_O 输出——由结合律，`W_UV·Σ(权重·c_KV(j))` 等价于 `Σ(权重·(W_UV·c_KV(j)))`，`W_UV` 整体被并进输出投影 `W_O` 一侧。**一句话：内容段只摸缓存里的 c_KV，不再砸开销还原出 k/v；位置段 k_R 是它自己的一小块，直接算完就丢。**

### 阶段五：KV cache 大对账（原文表 1）

```
机制         每token每层元素数            备注
MHA          2·n_h·d_h·l                  强
GQA          2·n_g·d_h·l                  中等
MQA          2·d_h·l                      弱
MLA          (d_c + d_hᴿ)·l ≈ 4.5·d_h·l   比MHA强(附录D.2)
```

代入 V2 的具体数字：`d_c=512`（=4·d_h）、`d_hᴿ=64`（=d_h/2）→ 每层 576 元素，约等于 **GQA 只有 2.25 个分组**的缓存开销，但性能超过 MHA。

**疑问点⑨：为什么 MLA 能"两头都占"，既比 MHA 强缓存又小，而 GQA/MQA 做不到？**
GQA/MQA 是**物理砍掉**一部分 k/v 头的容量，损失是硬的、不可补偿。MLA 砍的是**临时表达所需的 bit 数（低秩压缩）**，每个头仍拿到独立还原出来的 k/v，各头容量无损——它省的是"存储用的位数"，不是"表达用的容量"。这就是"stronger than MHA with a much smaller cache"的来源（原文 2.1.4）。

## 机制二：DeepSeekMoE——一次路由与均衡推演

### 阶段零：装备

每个 MoE 层：**2 个共享专家**（每个 token 必过，负责公共知识）+ **160 个路由专家**（每个 token 只选 6 个，K_r=6），每个专家中间维度 1536（原文 3.1.2）。第一层例外：仍是普通 FFN。

```
式20: h′_t = u_t + Σi(sh FFN) + Σi=1..N_r  g_i,t·FFN_i^(r)(u_t)
式21: g_i,t = s_i,t ， 若 s_i,t ∈ Topk({s_j,t}, K_r)；否则 0
式22: s_i,t = Softmax_i( u_tᵀ·e_i )        e_i = 第 i 个路由专家的质心
```

**疑问点⑩：门控 K 个里为什么直接拿 softmax 亲和度当权重，不再乘个可学习缩放？**
`g_i,t=s_i,t` 是"软中带硬"：不是纯 top-k 二值门（丢幅度信息），也不再额外套一套门控参数——softmax 已经把分数归一到"占总注意力多少"，天然就是权重，参数省、逻辑顺，且和式 23–25 的均衡损失互相独立、不打架。

**疑问点⑪：专家切得这么细（160 个、每个才 1536 维中间维），不嫌碎吗？**
这恰是 DeepSeekMoE 的两条腿（引 DeepSeek-MoE 论文）：(a) **细粒度切分**——同样的激活参数量切成更多小专家，每个专家只需精通更窄的知识，专精度更高；(b) **共享专家隔离**——把"所有 token 都要的公共知识"（如句法、常用搭配）锁进 2 个必过的共享专家，不浪费路由专家的容量去重复学公共知识。原文 2.2.1 明说：同等激活/总参数下 DeepSeekMoE 大胜 GShard 类传统 MoE。

### 阶段一：设备受限路由（Device-Limited Routing）

MoE 用专家并行时，160 个路由专家被摊到多台设备。一个 token 若被分给 6 个散布在 6 台设备上的专家，就得做 6 路通信——细粒度专家越多，通信越贵。V2 的开关：**先挑设备、再挑专家**——

```
1) 对 token 算 160 个亲和度 s_i,t
2) 按专家所属设备聚合分数，选出"含有最高分专家的" M 台设备（M=3，D=8）
3) 只在这 3 台设备的专家里做 top-K 选出 K_r=6 个专家
```

**疑问点⑫：先选设备会不会把"更好的专家"挡在门外？**
会放弃一点选择面，但原文 2.2.2 给了实验结论：**M≥3 时，设备受限路由的性能"大致追平无约束 top-K"**。通信成本从"最多 6 台设备"被摁到"最多 3 台"，换来的性能损失摆不到台面上——这是典型的"约束优化里取 Pareto 前沿"的取舍。

### 阶段二：三个辅助损失——把负载压平（本文实际采用的均衡方案）

为什么必须干预 routing：负载不均 → 某些专家嫌不够训练（routing collapse，原文引文）+ 专家并行下，慢设备拖住全队。V2 上的是**三个辅助损失**：

```
① 专家级 L_ExpBal = α₁ · Σi=1..N_r  f_i · P_i            (式23)
   f_i = (N_r/(K_r·T)) · Σt 1[ token t 选了 专家 i ]      (式24)  ← 选中频率（不可导）
   P_i = (1/T) · Σt  s_i,t                              (式25)  ← 平均亲和度（可导）
② 设备级 L_DevBal = α₂ · Σi=1..D  f′_i · P′_i             (式26–28)
   f′_i = 组内专家 f_j 的均值；  P′_i = 组内专家 P_j 之和
③ 通信级 L_CommBal = α₃ · Σi=1..D  f″_i · P″_i            (式29–31)
   f″_i = (D/(M·T)) · Σt 1[ token t 被发到设备 i ]          (式30)
   P″_i = 组内专家 P_j 之和                                (式31)
```

**疑问点⑬：f_i 明明是"数了一下选中几次"的离散计数，梯度怎么流进去的？**
关键在乘积结构：`f_i·P_i` 里 **f_i 是常数因子、P_i 是可导量**。这个损失的梯度全走 P_i：哪路专家被选择得太多（f_i 大），就把那路专家的平均亲和度 P_i 往下压。路由分数被压 → 后续概率被调低，选中的频次自然回落。**f_i 负责"发现谁太热"，P_i 负责"提供可拧的旋钮"。**

**疑问点⑭：已有专家级均衡了，为什么还要设备级和通信级两张网？分工不一样：**
- 专家级：怕 routing collapse（某路专家饿死）——模型质量的保险。
- 设备级：怕某台设备的**计算**吃太多，泡沫拖慢整体 step 时间——训练吞吐的保险。
- 通信级：设备受限路由只保证**每台设备最多发** M·T 份隐藏态，但没保证**每台设备收到的量**均衡；如果大家都往同一台设备挤，接收端瓶颈照样卡。通信损失把"接收量也均衡"补上（原文 2.2.3 第3段）。

超参（原文 3.1.2）：α₁=0.003、α₂=0.05、α₃=0.02；D=8、M=3。

### 阶段三：token 丢弃——辅助损失不能保证"绝对平"

均衡损失是"软引导"，不保证严格均衡；为兜底，训练再加一层**设备级 token 丢弃**：每台设备的计算预算定为 capacity factor=1.0，超出的 token 按亲和度由低到高丢弃。但保障两件事（原文 2.2.4）：

- 约 **10% 的训练序列**永不丢弃任何 token（保证这部分序列的语义完整，供最终评测一致对齐用）；
- 推理时可以灵活选择丢/不丢，且保持"训练-推理一致性"。

## ⚠ 一处更正：「无辅助损失均衡」不在本文里

很多解读（包括本笔记最初的大纲）把「专家带可训练偏置 b_i、偏置只调路由不进梯度」的无辅助损失均衡归到 V2。**经核对原文 2.2.3 与全部公式（式 23–31），V2 用的是三个辅助损失，全文没有出现无辅助损失偏置均衡。它出现在 DeepSeek 后续工作（DeepSeek-V3，arXiv:2412.19437）中**，读 V2 时请以本文自己的"三损失＋设备受限路由＋token 丢弃"为准。同样地，术语「DEC」在本篇中未出现，这里对应的机制叫 **Device-Limited Routing（设备受限路由）**。

## 全局数据流总表

| 阶段 | 谁在动 | 产出 | 缓存/通信代价 |
|---|---|---|---|
| MLA-压缩 | `W_DKV` 降维 | `c_KV`(512维) | ★进缓存 |
| MLA-还原 k/v | `W_UK`,`W_UV` 升维 | `k_C`,`v_C`(各128头) | 临时算完即丢 |

| MLA-吸收 | `W_UQᵀW_UK`并矩阵、`W_UV`并入`W_O` | 分数与输出直接从 `c_KV`/`c_Q` 算 | 省去还原 k/v 的重活 |

## 所有疑问点速查

| 疑问 | 答案 |
|---|---|
| 512 维装得下 16384 维的 k+v？ | 低秩赌注，附录D.2实证：更省还更强 |
| 训练要还原 k/v，那压缩图啥？ | 省的是随上下文积累的缓存，不是训练显存 |
| 压缩 Q 省不了缓存，图啥？ | 省训练时的激活内存（原文原话） |
| RoPE 和压缩为什么冲突？ | RoPE 夹在 `W_UQ` 与 `W_UK` 之间破坏吸收 → 矩阵乘不交换 → 得重刷前缀 k |
| `k_R` 为什么不走压缩线？ | 它位置敏感、只有64维，且独立通路方便 YaRN 只动它 |
| 一共缓存什么、多大？ | `c_KV`(512)+`k_R`(64)=576 元素/token/层 |
| `W_UK` 怎么"没被用"却还算对分数？ | 结合律把 `W_UQᵀ·W_UK` 并成预合并矩阵，直接乘缓存里的 c_KV |
| v 侧怎么免算的？ | `W_UV` 被吸收进输出投影 `W_O`，等效省去还原 v_C |
| ≈GQA 2.25 组怎么算的？ | (512+64)/(2·128)=2.25，d_c=4d_h、d_hᴿ=d_h/2 |
| 门控为什么直接用 softmax 亲和度？ | 已归一的"占据权重"，叠参数反而啰嗦还和均衡损失纠缠 |
| 160 专家会碎吗？ | 细粒度+共享专家=同等激活量更高专精度（vs GShard 实证优势） |
| 受限路由会错过好专家吗？ | M≥3 实验显示性能追平无约束 top-K（原文2.2.2） |
| f_i 不可导，辅助损失梯度从哪来？ | 梯度全走可导的 P_i；f_i 只负责"指谁太热" |
| 三个辅助损失各管什么？ | 专家级(模型质量) / 设备级(计算) / 通信级(接收端均衡) |
| token 丢弃干嘛？ | 兜底硬均衡；10% 序列豁免保证评测一致性 |

## 一句话总括

**MLA 把每个 token 的 k,v 联合低秩压进 512 维 latent `c_KV`（缓存它+64 维解耦 RoPE key `k_R` = 每 token 每层 576 元素 ≈ GQA 2.25 组），推理时用矩阵吸收让内容段直接在 `c_Q` 与 `c_KV` 上做注意力、彻底免掉"从 latent 还原 k/v"的重活；RoPE 敏感的位置不走压缩、由独立小路（每头小 q + 共享小 k）承载。DeepSeekMoE 用细粒度 160 专家 + 2 共享专家提升专精度，靠"先选 3 台设备再 top-6"摁住通信，靠三个辅助损失（专家/设备/通信均衡）+ token 丢弃稳住负载。** 相较 DeepSeek 67B：训练省 42.5%、KV cache 减 93.3%、最大生成吞吐 5.76 倍——一次教科书式的"用架构设计换真金白银性价比"。注意：**「无辅助损失偏置 b_i 均衡」不是本文的机制**，那是后续 DeepSeek-V3 的工作，读这篇别串门。
