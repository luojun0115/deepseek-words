# 动态平铺 × DeepSeekMoE：一张高分辨率长图的完整旅程（含所有疑问点）

## 角色与核心思想

DeepSeek-VL2 是 LLaVA 式三件套：**视觉编码器（SigLIP-SO400M-384）→ VL 适配器（2×2 pixel shuffle + 两层 MLP）→ MoE 语言模型（DeepSeekMoE + MLA）**。相对前代 DeepSeek-VL 的两大升级，分别管着这次的两大痛点：

- **痛点一：高分辨率图进不去**。老 DeepSeek-VL 用双编码器（SigLIP 出 384×384 粗特征 + SAM-B 出 1024×1024 细特征），上限被 1024×1024 的死分辨率锁住。信息图（InfographicVQA）、密排 OCR、细粒度视觉定位这类任务里的图，分辨率更大、长宽比更极端，硬压进 1024×1024 只能把小字压成马赛克。
- **痛点二：激活参数太贵**。稠密模型（如 InterVL2、Qwen2-VL）每 token 全量前向。VL2 系列换 MoE：总参数 3B/16B/27B，激活只有 0.57B/2.4B/4.1B——加上 MLA 把 KV cache 压成潜向量，单卡部署只要 10GB/40GB/80GB 显存。

**整套推演里谁在动**：图片先被"切"（动态平铺），切出来的 tile 各自过同一个视觉编码器，变成 token 后按阅读顺序排版（缩略图在前 + 分隔符 + tile 网格带换行符），再整体塞进 MoE LLM。图片搬家，模型的"词汇表"就是在读这串带版式标记的视觉 token。

下面以一张 **2304×1536（3:2 长宽比）** 的图为主角，走完全程。

## 阶段一：选切法 —— 在候选网格里挑 padding 面积最小的

视觉编码器 SigLIP 是在 384×384 上预训练的，"底座分辨率"动不了，所以 DISAI 的思路不是改变编码器，而是**让图去凑编码器**：把任意大小的图切进一张 m×n 的 tile 网格。

候选分辨率集合（原文公式，纯文本抄写）：

```
C_R = { (m×384, n×384) | m、n 为正整数，1 ≤ m、n，且 m×n ≤ 9 }
```

m:n 就是允许的长宽比。对输入 (H, W)，对每个候选都算一遍"要补多少 padding 才能装下这张图"（原文脚注：先 resize 到长边恰好匹配目标分辨率、另一维保持原始长宽比，再 pad），**选 padding 面积最小的那个**。

主角图 2304×1536 走一遍：

```
候选 (3,2)=1152×768：长边 2304→1152（缩 1/2），另一维 1536×(1152/2304)=768
                    → 恰好放下，padding = 0  ← 选中
候选 (2,2) =768×768 ：需把长边压到 768，另拉高 pad 至 768
                    → 大量缩放 + 两键 padding，padding 面积大
候选 (3,3) =1152×1152：上下各 pad 一大片空白
                    → padding 面积大
```

**疑问点①：为什么要按 padding 面积挑，不按"化整为零就行"随便切？**
任意切法其实总能让拓扑成立，但错误的方向——为了切而切。padding 面积是唯一可计算的"扭曲代价"：pad 得越少，原图被缩放的倍数越小、空白边越窄，小字和细纹理活下来的概率越高。(3,2) 是这张图的零扭曲解，比(2,2)的"先压 1/2 再拉白边"多保存了 4 倍线性分辨率。

**疑问点②：m×n ≤ 9 这个上限为什么是 9？**
原文给的理由是"计算效率与上下文长度管理"——每 tile 编码后压缩成 196 个 token（阶段三），但编码器侧每个 tile 要跑 27×27=729 个 patch 的注意力，9 块已是信息量/token 数/计算量的三重预算线。极端长图确实会切走更多，但对一张 9×1 的超长条图，9 块 tile 已覆盖 3456 个有效像素高，之后的缝隙会被全局缩略图兜底。

## 阶段二：切块编码 —— 所有 tile 过同一个 SigLIP

被选中的分辨率上，图被切成 **m×n = 3×2 = 6 个 384×384 局部 tile，外加 1 张整图缩略图 tile**（整图压成 384×384 的全局视图，原文只说"加一张 global thumbnail tile"，缩放细节未展开）。7 块 tile 全部馈给**同一个** SigLIP-SO400M-384，每块产出 **27×27 = 729 个 1152 维的视觉 embedding**。

```
原始图 2304×1536        选定 (3,2) → 1152×768        tiles: 3 列 × 2 行 + 缩略图
┌───────────────┐      ┌──────┬──────┬──────┐      ┌───┬───┬───┐
│               │      │ tile1│ tile2│ tile3│      │t1 │t2 │t3 │
│               │ resize ├──────┼──────┼──────┤  切  ├───┼───┼───┤
│               │ ────→ │ tile4│ tile5│ tile6│ ──→  │t4 │t5 │t6 │
│               │      └──────┴──────┴──────┘      └───┴───┴───┘
└───────────────┘                                  + [整图缩略图 tile]
```

这里和"把大图直接喂 ViT"的视觉编码器差异最大：ViT 都是**全局注意力**，patch 数翻倍，注意力平方跟着翻倍（自注意力是 O(N²)）。动态平铺则**每个 tile 独立编码、注意力只在 tile 内部局部进行**——729 个 patch 的规模无论图多大都不变，原文原话是"保留了局部注意力 ViT 的优点，避免随分辨率的二次方计算扩展"。

把 1152×768 直塞给 ViT 当参考系：图被切成 patch 后约 82×55 ≈ 4500 个 patch token，一次注意力是 ≈ 4500² ≈ 2000 万次打分；平铺后是 7 个 tile 各 ≈ 729² ≈ 53 万次，合计 ≈ 370 万次，便宜一个数量级，而且每块 tile 的有效分辨率反而**更高**（局部 384×384 全分辨率， versus 全图硬缩）。

**疑问点③：tile 之间的边界不就"断"了吗？跨边界的内容连续性怎么办？**
这正是该机制最被追问的地方，原文对此着墨不多，只交代三件事：每 tile 经共享 ViT 独立编码；排列上有全局缩略图兜底全局布局；tile 序列（阶段三）按原位顺序拼接后交给 LLM 自注意力跨 tile 聚合。原文**没有**描述重叠切分或跨边界等边缘处理——此点如实说明，不编造。可推知的取舍是：边界"拐弯"处（跨人行横字、跨边界表格线）局部 tile 各看一半，由 LLM 在注意力阶段把两块各自看到的一半重新拼合。

**疑问点④：为什么就算并列塞了局部 tile，仍要费一张缩略图？**
两个角色。一，局部 tile 各自守着 384×384，谁也不知道整图的布局——"这个区域是正文还是页眉""箭头从哪指向哪"必须看全图；缩略图提供全局视角。二，阶段三的排版正是"缩略图 | 分隔符 | tile 网格"，缩略图先入序列，给 LLM 一个"这张图整体长什么样"的观察，之后细读局部时才有参照。

## 阶段三：token 压缩与排版 —— 2×2 pixel shuffle + 两类特殊 token

每 tile 的 729 个 embedding 直接送进 LLM 太多（7 块就是 5103 个 token），先 **2×2 pixel shuffle**：2×2 邻接的 4 个 embedding 捆在一起，token 数 ÷4，**27×27 → 14×14 = 196 个 token/tile**。维数从 1152 变成 1152×4=4608 的拼接（随后由两层 MLP 投影到 LLM 的嵌入空间）——信息不丢，换空间换压缩。

然后按阅读顺序排版，插三类特殊 token：

```
[缩略图序列: 196 token + 14 个 <tile_newline>（每行行尾一个，共 14 行）] = 210
↓
<view_separator>                          ← 缩略图与局部 tile 之间的界碑
↓
[6 个局部 tile 拼成 (3×14)=42 行 × (2×14)=28 列，
 每行行尾补一个 <tile_newline>，共 42 个]
```

总视觉 token 数（原文公式）：

```
总数 = 210 + 1 + m_i×14 × (n_i×14 + 1)
主角图(m=3,n=2): 210 + 1 + 42 × 29 = 1429 个 token
最坏(m×n=9, 如9×1): 210 + 1 + 126 × 15 = 2101 个 token
```

**疑问点⑤：2×2 像素 shuffle 凭什么敢压 4 倍，信息不糊吗？**
它不是池化丢信息，而是**变基**：4 个相邻 1152 维向量直拼，随后 MLP 学会把"这 4 个 patch 联合说了什么"映射成 1 个 LLM token。图像相邻 patch 本来就高度相关（红字旁边是同一个红字），4 合 1 的冗余远大于信息损失。对照老 DeepSeek-VL：SAM-B。这一步把进入 LLM 的视觉 token 从 729/tile 砍到 196/tile，是在不动模型结构的前提下控制上下文长度的开关。

**疑问点⑥：`<tile_newline>` 为什么缩略图 14 个、局部网格 42 个？它是给谁看的？**
是给 LLM 看的排版记号。缩略图 14×14 个 token，每行 14 个，行尾补一个换行 → 14 个；局部网格拼成 42 行（每行 = 一段 tile 内的一横条 + 方向信息），行尾同样补 → 42 个。它们模仿了读者看图时"逐行扫"的结构单位——LLM 里的模型读文本习惯了换行符，把视觉序列也编成"一张图换一次行"的语序，注意力分配才有结构可依。

**疑问点⑦：>2 张图一起进来时为什么干脆关掉动态平铺？**
每张图平铺后 token 至少过千，两张高分辨率图就是两三千。上下文窗口和注意力计算量都受不了，于是超过 2 张时降级为单 384×384 编码。这也暗含一个工程判断：动态平铺是为"给一张重要图配足算力"设计的，不是为"扫一堆图"设计的。

## 阶段四：进 MoE 语言模型 —— MLA + 共享/路由专家 + 偏置修正

排版完的视觉 token 序列经两层 MLP 投到 LLM 嵌入空间，与文本 token 混合喂给 DeepSeekMoE LLM。表1（原文表格）三档配置：

| 项 | VL2-Tiny | VL2-Small | VL2 |
|---|---|---|---|
| LLM 总参数 | 3B | 16B | 27B |
| 激活参数（LLM） | 0.57B | 2.4B | 4.1B |
| 注意力 | Multi-Head | MLA（rank=512） | MLA（rank=512） |
| 路由专家数 | 64 | 64 | 72 |
| 共享专家 | 2 | 2 | 2 |
| Top-K | 6 | 6 | 6 |
| 路由函数 | Softmax | Softmax | **Sigmoid** |
| 专家偏置修正 | ✗ | ✗ | ✓ |

共享专家：每个 token **必过**这 2 个专家（装通用知识，不参与"分单"）；路由专家：按 Top-K=6 从 64/72 个细粒度专家中动态选 6 个。"细粒度专家 + 少数共享"就是 DeepSeekMoE 的核心配方——把一个稠密 FFN 拆成更多小专家，让单 token 的样本组合自由度更高，同时激活参数被 Top-K 卡死。

MoE 训练里各专家分单不均的老大难，VL2 沿用 DeepSeek 的做法：给每个路由专家加一个**全局偏置项**（原文引 DeepSeek-V3 的做法），用它实现了"不用额外辅助损失的负载均衡"，训练代价更低。

**疑问点⑧：论文明说用 MLA 压 KV cache，Tiny 怎么反而用普通 MHA？**
原文只陈述事实没讲原因（表1 里 Tiny 一栏就是 Multi-Head Attention），不替作者编理由。但有个能对应上的结构事实：MLA 的收益是把 KV cache 压进潜向量 rank=512，省的是**序列长 ×KV 宽**的显存——Tiny 只有 12 层、1280 维嵌入、总参 3B，KV cache 本就小；而层数/宽度上去了，KV cache 便宜的收益才值得引入额外的矩阵变换。示范给结论：此处确为"待核实"，原文未解释。

**疑问点⑨：Sigmoid 路由 + 偏置修正，为什么只有最大的 VL2 档用？**
表1 只给出了配置差异，趋势与 VL2 沿用 DeepSeek-V3 的演化路径一致（V3 正是 Sigmoid 门控 + 偏置修正的组合）；最大档与 V3 基座血缘最近，直接继承其成熟配置，Tiny/Small 保留 Softmax。原文还给了一个可观察的佐证：训练超参里 Tiny/Small 的辅助损失权重是 0.001，VL2 反而降到 0.0001——大档的负载均衡更多交给偏置修正，辅助损失退到保底。

**疑问点⑩：为什么视觉编码器那一侧不用任何 MoE，全靠 LLM 扛？**
视觉 token 密集（本例 1429 个视觉 token 大约占序列大半），如果它们也全去路由专家，专家间接单会溃散。把 MoE 的"稀疏激活收益"只放在文本与混合序列共用的 LLM 上，视觉编码器侧固定用同一个 SigLIP（所有 tile 共享）——同一个编码器被 7 块 tile 复用，本身就是另一种"稀疏化"：参数 0.4B，路人一份。

## 阶段五：三阶段训练配方 —— 没有 DPO

仔细看原文第4节，确为**三阶段**（对齐 → 预训练 → SFT），没有第四阶段，也没有 RL/DPO 环节，此点以原文为准：

```
阶段1（对齐）: 冻结 LLM，训练视觉编码器 + 适配器 MLP，数据 ShareGPT4V（约 1.2M 条目）
                ※ 与 LLaVA 系"双冻结"不同：VL2 此阶段连视觉编码器一起调，
                  为的是让固定 384 的 SigLIP 学会处理动态高分辨率输入
阶段2（预训练）: 全参数解锁，约 800B 视觉-文本 token
                （VL 数据 : 纯文本 = 70% : 30%，后者直接取自基座 LLM 预训练语料）
阶段3（SFT）  : 全参数解锁，约 20B token，只监督回复与特殊 token（系统/用户提示词被 mask）
```

全阶段统一原则：**只对文本 token 计算下一个 token 预测损失**。关键超参（表2）：视觉编码器学习率 ×0.1（防止把预训练好的表征冲散）；MoE 辅助损失权重 Tiny/Small=0.001、VL2=0.0001；VL2 的专家偏置修正步长三阶段为 0 / 0.001 / 0。整个系列训练用时 7/10/14 天，分别用 16/33/42 台 8 卡 A100 节点。

**疑问点⑪：损失只算文本 token，视觉 token 不参与损失，模型怎么"学会看"？**
"看"是通过条件间接学会的：视觉 token 在注意力里是**条件**，不是**监督目标**。预测"这张图的回答下一个字是什么"必须用足图里的信息，梯度穿过注意力路径自动回流到视觉编码器与适配器。不强制视觉 token 自重建图形（那会逼模型浪费容量在做图这种下游无关的任务上）也是省算力的选择。

**疑问点⑫：视觉编码器学习率 ×0.1 是护什么？**
护预训练表征。SigLIP-SO400M 是在几十亿图文对上预训练的底座，动态平铺只是"输入空间"变了（单图 → 图块组），其内部表征能力不该被推倒重来。×0.1 让它"适应但不重塑"；真正要学的映射关系主要落在适配器 MLP 和 LLM 那边。

## 阶段六：产出 —— grounding 的回答长什么样

Visual grounding 是 VL2 新增的核心能力，训练数据格式（原文原样抄）：

```
提示: Locate <|ref|><query><|/ref|> in the given image.
回答: <|ref|><query><|/ref|><|det|>[[x1, y1, x2, y2],…]<|/det|>

坐标 (x1, y1) 左上角、(x2, y2) 右下角，
按图片分辨率归一化到 0–999 的整数区间。
```

`<|ref|>` `<|det|>` 等是特殊 token；`<query>` 可为类名（"car"）或描述（"最左边的人"）；训练时**故意构造"目标不在图中"的负样本**练稳健性。SFT 阶段还加料：查询短语翻译成中文、in-context 定位（第一图用框/圈高亮参照物，要求在第二图找同类物）、以及 `<|grounding|>` 开头的坐标穿插式对话——回复像在"画框讲解"，让直接落到具身 AI、GUI 代理这类用途上。

**疑问点⑬：grounding 为什么从这套架构里受益最大？动态平铺到底怎么帮它？**
链条是"分辨率里的细节 + 位置表示方式"。一，"左边第二个小杯子"这类目标通常只占几十分之一画面：整图压 384 时它只剩十几个 patch，几乎淹没；平铺后它有整块 tile 的 196 token 可用，细粒度是几千量级。二，坐标按**原图**归一化到 0–999：tile 是怎么切的、选了哪个候选分辨率，回归出的框始终指向同一原图坐标系——切图切出的"世界"没有被改变。

## 关键数字与实验

## 全局数据流总表

| 步骤 | 谁在动 | 产出 | 代价 |
|---|---|---|---|
| 1 选切法 | 对每个候选算 padding 面积 | (m,n)=(3,2)，零 padding 拼接 | 每候选一次尺寸计算，无模型 |
| 2 切块+缩略图 | resize + pad + 切 6 块 + 缩略图压 384 | 7 个 384×384 tile | 简单几何操作 |
| 3 编码 | 同一个 SigLIP-SO400M-384 | 7 × (27×27=729) 个 1152 维 embedding | 注意力只在 tile 内（≤729²） |
| 4 token 压缩 | 2×2 pixel shuffle | 每 tile 196 token（27×27 → 14×14） | 定向重排，无参数 |
| 5 排版 | 插 `<tile_newline>`×56、`<view_separator>`×1 | 1429 个视觉 token（公式驱动） | 索引计算 |
| 6 投影 | 两层 MLP | 对齐到 LLM 嵌入空间 | 轻量前向 |
| 7 LLM 推理 | DeepSeekMoE：6 个路由专家 + 2 个共享 | 下一个 token 分布 | 仅激活 4.1B 总参的 27B |
| 8 输出 grounding | 特殊 token 框架生成 | 文本 + `<|det|>[[x1,y1,x2,y2]]` | LLM 前向的正常开销 |

## 所有疑问点速查

| 疑问 | 答案 |
|---|---|
| ① 为什么按 padding 面积挑切法？ | padding 是可算的"扭曲代价"，最小即零扭曲解，字符细纹最易存活 |
| ② 上限为什么 m×n ≤ 9？ | tile 数受 token 预算和二次方计算约束，9 是作者的效率预算线 |
| ③ tile 边界断了怎么办？ | 原文未提及重叠/跨边界处理，实事求是可以推断的三件：局部独立编码、缩略图兜全局、LLM 注意力聚合 |
| ④ 为什么还要缩略图 tile？ | 提供 tile 各自看不到的全局布局与指向性参照，也是序列排版的锚 |
| ⑤ 2×2 shuffle 敢压 4 倍不糊吗？ | 非池化而是重组：4 个 1152 维直拼由 MLP 学映射，相邻 patch 冗余远大于信息损失 |
| ⑥ `<tile_newline>` 为什么分 14 / 42 个？ | 分别对应缩略图 14×14 与局部拼接网格 42 行的行数，按行补换行 |
| ⑦ >2 图为何关闭动态平铺？ | token 预算护 AvB 的"单重点图"设计，防多图时上下文吃紧 |
| ⑧ Tiny 为何不用 MLA？ | 原文未解释，为"待核实"项，仅知其 12 层/1280 维 KV cache 本就小 |
| ⑨ Sigmoid 路由为何只在最大档？ | 最大档血缘最近 V3 成熟配置；辅助损失降档（0.001→0.0001 转为佐证） |
| ⑩ 为何视觉侧不上 MoE？ | 视觉 token 太密集，路由专家易溃散；同一编码器复用本身已是参数分摊 |
| ⑪ 视觉 token 无损失，怎么学会看？ | 视觉 token 是条件，梯度经注意力回流；不强制重建图形省容量 |
| ⑫ 视觉编码器 LR ×0.1 护什么？ | 防止预训表征被冲散：适应新输入空间，不重塑能力 |
| ⑬ grounding 是怎么被动态平铺放大的？ | tile 内细粒度足够小目标 + 坐标归一化到原图 0–999，位形世界不因切图而变 |

---

## 一句话总括

**一张任意长宽比的高分辨率图进来，先在 m×n ≤ 9 的候选分辨率网格里选 padding 面积最小的切法，切出 384×384 的 tile + 一张全图缩略图，全部过同一个 SigLIP（注意力只限 tile 内部，躲开全局注意力的二次方开销），2×2 pixel shuffle 把 729 token/tile 压到 196，再按"缩略图 + 分隔符 + 行换行符"的阅读顺序排版成上千个视觉 token 塞进 LLM。而 LLM 端用 DeepSeekMoE（2 个共享专家 + 64/72 个路由专家 Top-K=6，最大档 Sigmoid 门控 + 专家偏置修正）加 MLA（KV cache 压成 rank=512 潜向量），27B 总参的模型每 token 只激活 4.1B，单独一卡 80GB 就能跑。** Zero-padding 选切保住细节，平铺注意力保住计算，排版 token 保住结构，稀疏 MoE 保住推理预算——四件事各占一环，最终让 4.5B 激活的模型在 DocVQA 93.3、RefCOCO 96.7 处逼近 ≥7B 稠密对手。
