# 一个 token 在 DeepSeekMoE 层的完整旅程（含所有疑问点）

## 角色与核心思想

- **要解决的问题**：传统 MoE（如 GShard 的 top-2、Switch 的 top-1）里，专家拿到的知识是「混着来的」——一个专家的招的人五花八门，被迫把多种知识塞进同一份参数（知识混合）；而不同专家又各自偷偷学了一套公共知识（知识冗余）。两大病合起来，就是「专家专业化程度不够」，离 MoE 的理论上限差一截。
- **两个药方**：① **Fine-Grained Expert Segmentation（细粒度专家切分）**——把 N 个粗专家每个切成 m 份，变成 mN 个细专家，每 token 激活 mK 个；切得越细，可组合方式指数级爆炸，组合越灵活，知识分解得越精确。② **Shared Expert Isolation（共享专家隔离）**——留 Ks 个「人人都走」的共享专家，专门收编公共知识，逼着其余路由专家不再重复学公共知识。
- **推演主视角**：盯住一个 token，看它穿过一层 DeepSeekMoE 的每一步——怎么被打分、怎么被挑中、怎么被加权、结果怎么拼回去。三大动人物：**router（打分器）**、**路由专家（等着被挑）**、**共享专家（无条件全勤）**。

---

## 阶段一：起点——标准 MoE 层是怎么算一个 token 的

Transformer 里，FFN 被 MoE 层替换。token t 走到第 l 层，先过 attention 得到 `u_tᴸ`，然后 MoE 层给出最终输出 `h_tᴸ`（原文式 1–5）：

```
打分:   s_i,t = Softmax_i( u_tᴸᵀ · e_iᴸ )         ← 对每个专家 i 算一次
取门:   g_i,t = s_i,t   若 s_i,t 属于 top-K 最大者（共 K 个非零）
              = 0       其他
合并:   h_tᴸ = Σᵢ g_i,t × FFN_i(u_tᴸ) + u_tᴸ
```

- `e_iᴸ` 是第 i 个专家的**质心向量**（可学习参数），router 就是「token 表示 · 质心」内积再 softmax。
- 非零门控只有 K 个 → 每个 token 只在 K 个专家里做 FFN 计算，这就是稀疏带来的省算力。
- 末尾 `+ u_tᴸ` 是残差：MoE 只负责「补知识增量」，原始信息原样保留。

**疑问点①：`e_iᴸ` 是什么？是专家的参数吗？**
不是专家参数，是 router 自己的参数（每个专家配一个质心向量）。专家 FFN 里是矩阵乘，router 里只是内积——内积便宜，所以是先「便宜地打分」再「贵地算专家」。

**疑问点②：门控值 g 直接用 softmax 分数，为什么不归一化到 1？**
top-K 之后 g 本来就只剩 K 个非零项，求和不必为 1——分数大小本身就是「贡献权重」。本文沿用这一常见做法，未做额外归一化。

---

## 阶段二：粗粒度 MoE 输在哪（本文的靶子）

原文点出两个病：

```
病1 知识混合: 专家数量少（比如 8 或 16 个），分到某个专家的 token
              必然五花八门 → 专家被迫把多种知识揉进同一份参数，
              而揉在一起的知识很难"同时被用好"。
病2 知识冗余: 不同专家招到的 token 有共同需求（公共知识）→
              多个专家各自学了一套公共知识 → 参数重复建设。
```

组合数视角（原文给的例子，N=16，top-2）：

```
粗粒度:   C(16, 2)  = 120 种专家组合
切成 4 份: C(64, 8)  = 4,426,165,368 种组合   ← 千万倍级别的爆炸
```

**疑问点③：top-2 只有两名裁判，怎么就「必然」不专了？**
不是裁判的错，是候选池的错。池子里只有 16 种「粗知识块」，一个专家吃到的 token 混着几种不相干的知识，它只能全都学。切细后每个候选更小更纯，同样的两个 token 需求，可以让「细专家 A+B」而不是「粗专家 X（被迫兼）」去覆盖——知识的分解粒度对了，每个参数才只干一件事。

---

## 阶段三：细粒度切分——每个粗专家切成 m 份

做法（原文式 6–8）：把每个专家 FFN 的**中间隐藏维度砍到 1/m**，粗专家变 m 个细专家；同时把激活数从 K 提到 mK：

```
总参数不变:   N 个粗专家  →  mN 个细专家（每个是原大小的 1/m）→ expert 参数总量 ≈ N × 标准FFN
算力不变:     每token激活 K 个 → mK 个细专家 → 激活FFN计算量 ≈ K × 标准FFN

打分:   s_i,t = Softmax_i( u_tᴸᵀ · e_iᴸ )     ← 在 mN 个候选上打分
取门:   g_i,t = s_i,t   若属于 top-mK
              = 0       其他
合并:   h_tᴸ = Σᵢ ( g_i,t × FFN_i(u_tᴸ) ) + u_tᴸ     i 遍历 1..mN
```

落到 DeepSeekMoE 2B（原文 4.2 节 Baselines）：m=4，共 64 个专家 = **1 共享 + 63 路由**，每个细专家是标准 FFN 的 0.25 倍大小；激活 `1 + 7`。

**算力守恒账**（对照表 1）：

```
GShard 2B:       top-2 粗专家 → 每层激活 2 × 1.0 = 2.0 份标准FFN计算
DeepSeekMoE 2B:  共享 1×0.25 + 路由 7×0.25 = 2.0 份标准FFN计算   ← 打平
两者激活参数都是 0.3B，每 2K token 都是 4.3T FLOPs（表 1）。
```

**疑问点④：专家变小了，单个专家表达能力不够，学了也白学吗？**
单个确实变弱，但语言知识的天然粒度本来就小——切细了正好对上。单个弱专家覆盖不了的需求，用「多个细专家的组合」覆盖，而组合数是指数级的（阶段二的 44 亿 vs 120）。所以不是「小专家凑合用」，而是「小知识配小专家、大需求配组合拳」。

**疑问点⑤：mK 个里挑 8 个，会不会挑错、挑散？**
router 还是同样一套（内积+softmax+top-K），变的只是候选更多。实践上靠负载均衡损失兜底（阶段五）。另外注意：挑得更细也意味着**容错更低**——阶段四的共享专家之一部分作用就是兜底通用需求，让路由失误的代价不至于太大。

---

## 阶段四：共享专家隔离——Ks 个「永远全勤」的专家

完整的 DeepSeekMoE 层（原文式 9–11）：

```
h_tᴸ = Σ (i=1..Ks)     FFN_i(u_tᴸ)              ← 共享专家：无 router、无门控，直算直加
     + Σ (i=Ks+1..mN)  g_i,t × FFN_i(u_tᴸ)      ← 路由专家：只在 Ks+1..mN 里挑
     + u_tᴸ                                                     ← 残差

g_i,t = s_i,t   若 s_i,t 属于 top-(mK−Ks)（在路由专家范围内选）
      = 0       其他
s_i,t = Softmax_i( u_tᴸᵀ · e_iᴸ )
```

**合并方式的关键**：共享专家的输出 `FFN_i(u_tᴸ)` 是**系数恒为 1 的加法项**，和路由专家的加权项并排加在一起，再统一加残差。它不过 router，所以无论什么 token 来，它的输出都在。

**配额账**：为了保持总算力不变，路由侧的激活数从 mK 减到 `mK − Ks`。各档模型（原文附录 A 表 7）：

```
2B:   1 共享 + 63 路由，激活 1 + 7（每个专家 0.25× 标准FFN）
16B:  2 共享 + 64 路由，激活 2 + 6（每个专家 0.25×）
145B: 4 共享 + 128 路由，激活 4 + 12（每个专家 0.125×）
共享专家 : 激活路由专家 ≈ 1 : 3（消融选定的比例，见阶段五后）
```

**为什么冗余知识会收敛进共享专家**：共享专家对每个 token 都生效，它的梯度来自**所有 token**——它学到的必然是「到处都要」的知识。路由专家则相反，只从自己被选中的那部分 token 拿梯度。两边的压力源不同，公共知识被压到共享一侧，路由专家被迫差异化，冗余自然下降。

**疑问点⑥：共享专家没有 router 择优，它会不会退化成一个普通的小 FFN，没花头？**
它确实结构上就是个永远开启的小 FFN——而这正是设计意图：等于每层免费挂了一个 mini dense FFN 兜住全体 token 的公共需求。它有没有花头由数据说话：把共享expert 禁掉、多激活一个路由 expert 补算力，Pile loss 从 1.808 暴涨到 2.414（原文 4.5 节）——它学到的根本知识，路由专家补不回来。

**疑问点⑦：既然是「人人都走」，为什么不留成 dense FFN 或多加 attention？**
因为它必须和路由专家**同构**才能参与下一层的统一计算与部署（每个 expert 结构相同，共 0.25× 大小）；更重要的是它的定位是「可插拔的公共知识容器」——消融（原文 Figure 3）显示从 GShard 里隔离出一个共享专家就能涨点，这说明收益来自「公共知识被单独圈养」这件事，而不是「多了一点 dense 容量」。

**疑问点⑧：Ks 个共享专家是「细专家」还是「粗专家」？**
细的。它们和其他细专家一样是 0.25×（145B 里 0.125×）的 FFN。共享专家的共享性来自「全 token 必须走它」，不是来自「更大」。

## 阶段五：负载均衡——不收拾 router 它就偷懒

自动学出来的 router 会扎堆（routing collapse：永远只选那几个专家，别的专家没得训练）。本文用两个损失约束（原文式 12–17）：

```
专家级: L_ExpBal = α1 × Σᵢ fᵢ × Pᵢ     i 遍历全部 N' = mN − Ks 个路由专家
        fᵢ = 被token选中的频次占比（选中记1，归一化）
        Pᵢ = 亲和度 s_i,t 在 batch 内的平均值
        → fᵢ、Pᵢ 都希望各专家均摊 → 乘积求和越小越均衡

设备级: L_DevBal = α2 × Σ_d f'_d × P'_d   d 遍历 D 组设备
        f'_d = 设备组内专家 f 的均值；P'_d = 组内专家 P 的求和
        → 只约束"每组设备的总计算量"均衡
```

用法的原则（原文 3.3）：**α1 设得很小（防 routing collapse 就够），α2 设得较大（保证设备间负载）**——「对专家负载过度约束会损害模型性能，但对设备计算量的必须硬约束」。实测：2B 用 α1=0.01（单卡部署无设备级损失）；16B 用 α1=0.001（每层所有专家同卡，不用设备级）；145B 用 α1=0.003 + α2=0.05（专家并行分布在 4 台设备）。

**疑问点⑨：专家切得越细，负载均衡是不是越难做？**
是。候选从 16 → 64/128，单个专家被选中的频次更稀疏，方差更大，routing collapse 风险更高。这正是论文要用显式损失压着的原因——而且故意用**小 α1**：只防崩，不求严格均衡，把「专家要不要绝对公平」留给模型自己决定。

**疑问点⑩：为什么设备级可以要求硬平衡，专家级反而不行？**
设备级失衡 = 某台卡成为计算瓶颈（等下一批），这是纯工程损失。专家级若强制绝对公平，router 会被迫把 token 派给并不合适的专家，直接伤模型质量。两个损失治的不是一种病，所以力度一宽一严。

**疑问点⑪：消融里说「共享:激活路由 ≈ 1:3 最好」，这个结论怎么来的？**
原文 4.4 节 Ratios Between Shared and Routed Experts：在最细粒度（64 专家）下，分别隔离 1、2、4 个共享专家，Pile loss 分别为 **1.808 / 1.806 / 1.811**——差异很小，但 1 个共享（对应共享:激活路由 = 1:3）略好，于是后续放大模型时固定这个比例。

## 阶段六：出层之后

- `h_tᴸ` 交付给下一层 attention，旅程继续。token 每穿过一个 MoE 层，都要重走一遍「打分 → 挑选 → 加权 → 合并」整套流程，且每层的路由选择相互独立。
- 16B/145B 有一个例外：**第一层不是 MoE**（原文 5.1.2：第一层的负载均衡收敛显著更慢，于是保留 dense FFN）。
- 每层内，这个 token 消耗的算力 = 共享专家（固定）+ mK−Ks 个路由专家（浮动）；整个 batch 的通信/计算模式由设备级均衡损失压平。

## 关键数字与实验

**主战场（原文表 1，2B / 100B token）**

| 指标 | Dense | Hash Layer | Switch | GShard | DeepSeekMoE |
|---|---|---|---|---|---|
| 总参数 | 0.2B | 2.0B | 2.0B | 2.0B | 2.0B |
| 激活参数 | 0.2B | 0.2B | 0.2B | 0.3B | 0.3B |
| Pile (Loss) | 2.060 | 1.932 | 1.881 | 1.867 | **1.808** |
| HellaSwag | 38.8 | 46.2 | 49.1 | 50.5 | **54.8** |
| TriviaQA (EM) | 4.9 | 6.5 | 8.9 | 10.2 | **16.6** |

**对标上限（原文表 2）**

| 指标 | GShard×1.5 | Dense×16 | DeepSeekMoE |
|---|---|---|---|
| 激活专家 | 0+2 | 16+0 | 1+7 |
| 专家参数总量 | 2.83B | 1.89B | 1.89B |
| 每2K token FLOPs | 5.8T | 24.6T | 4.3T |
| Pile (Loss) | 1.808 | 1.806 | 1.808 |

→ DeepSeekMoE 用 1.5 倍算力之差打平 GShard×1.5；几乎贴上「16 倍 FFN 参数的 dense 模型」这条理论上限（PileLoss 1.808 vs 1.806）。

**消融（原文 4.4 节配套 Figure 3，等参数等算力对比）**
- 从 GShard 里隔离 1 个共享专家 —— 多数 benchmark 提升。
- 细粒度持续加细（GShard → 32 专家(1+31) → 64 专家(1+63)）—— 性能持续提升。
- 共享:激活路由 = 1/2/4 共享专家试验，Pile loss 1.808 / 1.806 / 1.811，选 1:3。
- 注：有一版流行说法提到「细粒度+共享专家训练前期落后、后期反超」的曲线；本论文抓到的正文与图注（Figure 3 为最终性能归一化对比）中未见此句，该表述出现在后续 DeepSeek-V2 等论文中——在此标注：**待核实**，本文正文能确证的是「同样算力下最终性能更优」。

**专家专业化证据（原文 4.5 节）**
- 逐个屏蔽 token 最想去的路由专家再测 Pile：DeepSeekMoE 比 GShard×1.5 更敏感 → 路由专家间冗余更低、更不可替代。
- 禁用共享 expert、补激活一个路由专家（算力不变）：Pile 1.808 → 2.414。
- 激活路由专家从 7 减到 4：Pile 才勉强追平 GShard（Figure 5）；干脆从头训一个「只激活 3 个路由专家」的模型（激活专家参数只有 GShard 的一半），仍**优于 GShard**（Figure 6）→ 激活参数里「有效参数占比」远高于 GShard。

## 全局数据流总表

| 步骤 | 谁在动 | 产出 | 代价 |
|---|---|---|---|
| 1. attention 出 u_tᴸ | attention 模块 | token 当前表示 | 常规 |
| 2. router 打分 | 质心 e_iᴸ | mN−Ks 个亲和度 s_i,t | 便宜（内积+softmax） |
| 3. top-(mK−Ks) | 选择 | Ks 个共享（无条件）+ mK−Ks 个路由名单 | 免费 |
| 4. 共享专家计算 | 共享专家 ×Ks | 恒定公共知识增量，系数 1 | 固定 |
| 5. 路由专家计算 | 被选中专家 | 各自输出 × 门控 g=s_i,t | 稀疏 FFN × (mK−Ks) |
| 6. 合并+残差 | 求和 | h_tᴸ = 共享Σ + g路由Σ + u | 免费 |
| 7. 交付下一层 | — | h_tᴸ 进下一层 attention | — |
| (训练附加) | balance loss | L_ExpBal(小 α1) + L_DevBal(大 α2) | 免费（不进推理） |

## 所有疑问点速查

| 疑问 | 答案 |
|---|---|
| 质心 e 是专家参数吗 | 不是，是 router 的可学习参数，只用内积打分 |
| 门控为什么不归一化 | top-K 后非零项求和不必为 1，分数大小即贡献权重 |
| top-2 为什么必然不专 | 候选池粒度粗，一专家被迫混学多种知识；切细后靠组合覆盖 |
| 专家变小会不会变弱 | 会，但知识天然粒度小，组合数指数级补齐表达能力 |
| 共享专家的输出怎么合并 | 系数恒为 1 的加法项，与路由专家加权和并排相加再上残差 |
| 共享专家会不会退化成没花头的普通 FFN | 消融反证：砍掉它 Pile 1.808→2.414，路由专家补不回来 |
| 共享专家是粗还是细 | 与路由专家同规格的细专家，共享的是「被谁使用」不是「多大」 |
| 算力怎么守恒 | 粗 top-2 = 2.0 份标准FFN；细粒度 = 1×0.25 + 7×0.25 = 2.0 份 |
| 为什么细粒度下更怕 routing collapse | 候选多、单专家命中更稀疏、方差大，所以配 balance loss 压着 |
| 专家级与设备级均衡力度为何一宽一严 | 专家级硬卡会伤模型，设备级失衡是纯工程瓶颈，必须硬卡 |
| 1:3 比例怎么定的 | 1/2/4 个共享专家实测 Pile 1.808/1.806/1.811，取略优的 1 个 |
| 第一层为什么不是 MoE | 第一层负载均衡收敛显著更慢，16B/145B 保留 dense FFN |

---

## 一句话总括

**把 2 个粗专家换成「1 个全勤共享细专家 + 7 选 mN 的路由细专家」（等参数等算力）：router 用内积在 63 个路由专家里打分，top-7 加权求和；共享专家不看 router、以系数 1 无条件并入，把「人人都需要」的知识锁死在自己参数里；软平衡靠两个损失（专家级防崩、设备级防瓶颈）。结果：同一算力下 Pile 从 GShard 的 1.867 降到 1.808，逼近 16 倍 FFN 的 dense 上限（1.806），且任务放大到 16B/145B 结论不变——省下的算力靠的不是玄学，是「知识拆得更细 + 公共知识不重复存储」。**
